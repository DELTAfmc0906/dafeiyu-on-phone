## 1. 忘了 `gradle-wrapper.properties`

**报错**
```
java.lang.RuntimeException: Wrapper properties file
'...\gradle\wrapper\gradle-wrapper.properties' does not exist.
```

**原因**：工程是手工搭的骨架，只从模板工程拷了 `gradlew` / `gradlew.bat` / `gradle-wrapper.jar`，
漏了这个 properties 文件。

**修法**：补上，并把 `distributionUrl` 指向腾讯云镜像（否则要从 services.gradle.org 拉，国内很慢）。

```properties
distributionUrl=https\://mirrors.cloud.tencent.com/gradle/gradle-9.8.1-bin.zip
```

## 2. `key.properties` 带 UTF-8 BOM 导致签名读不到

**报错**
```
* Where: Build file '...\app\build.gradle.kts' line: 29
* What went wrong:
getProperty(...) must not be null
```

**排查过程**：对比了本项目与能正常构建的 HelloAndroid 的 `key.properties`，发现字节差异：

```
本项目     前3字节 = 239,187,191   ← UTF-8 BOM (EF BB BF)
HelloAndroid 前3字节 = 35,32,231     ← "# " 无 BOM
```

BOM 会粘在**第一个键名**上，`storeFile` 实际变成了 `\uFEFFstoreFile`，
所以 `getProperty("storeFile")` 返回 null。

**修法（两道）**：

1. 写文件时用 `UTF8Encoding($false)` 明确不要 BOM
2. 构建脚本里加防御，主动剥掉 BOM 键名：

```kotlin
val bomKeyName: String? = keystoreProps.stringPropertyNames()
    .firstOrNull { it.startsWith('\uFEFF') }
if (bomKeyName != null) { /* 改名 */ }
```

> 教训：`.properties` / `.xml` 之外的配置文件尽量别有 BOM，
> Windows 上的 `Set-Content -Encoding UTF8`（PowerShell 5.1）会加 BOM。

## 3. Kotlin DSL 类型推断递归

**报错**
```
e: app/build.gradle.kts:17:22: Type checking has run into a recursive problem.
   Easiest workaround: specify the types of your declarations explicitly.
e: app/build.gradle.kts:17:36: Unresolved reference 'stringPropertyNames'.
```

**出错的写法**
```kotlin
val keystoreProps = Properties().apply {      // 没写类型
    if (...) keystorePropsFile.inputStream().use { load(it) }
}
// 后面又引用 keystoreProps.stringPropertyNames() ...
```

**原因**：`apply {}` 的接收者类型依赖 `keystoreProps` 的推断类型，
而 `keystoreProps` 的类型又依赖 `apply {}` 内部的引用 —— 循环了。

**修法**：显式声明类型，并且不要在 `apply` 块里回引自己。

```kotlin
val keystoreProps: Properties = Properties()
if (keystorePropsFile.exists()) {
    keystorePropsFile.inputStream().use { stream -> keystoreProps.load(stream) }
}
```

> 同类问题也出现在 `java.util.Properties()`：Kotlin DSL 里 `java` 被 Gradle 的
> `java` 扩展遮蔽，必须 `import java.util.Properties` 后用短名。

## 4. Kotlin 字符串模板里中文紧跟变量名

**报错**
```
e: Lines.kt:85:67 Unresolved reference 'city今天'.
```

**出错的写法**
```kotlin
fun weatherLine(city: String, temp: String, desc: String) = "$city今天${temp}°，天气$desc"
```

Kotlin 把 `city今天` 当成一个标识符了 —— 它允许标识符里含中文，
所以 `$city今天` 会被解析为变量 `city今天`。

**修法**：用花括号把变量名括起来。

```kotlin
"${city}今天${temp}°，天气$desc"
```

## 5. `coerceAtLeast` 的类型不匹配

**报错**
```
e: PetEngine.kt:336:63 Argument type mismatch: actual type is 'Float', but 'Int' was expected.
```

**出错的写法**
```kotlin
val hiX = (screenW - petWidth - dp(40)).coerceAtLeast(loX + 1f)
//    ^^^ Int 表达式                              ^^^ Float 参数
```

**修法**：先转 Float 再 coerce。

```kotlin
val hiX = (screenW - petWidth - dp(40)).toFloat().coerceAtLeast(loX + 1f)
```

## 6. `||` 与换行导致的布尔判断错位

**报错**
```
e: SettingsActivity.kt:319:17 Condition type mismatch: inferred type is 'Int' but 'Boolean' was expected.
e: SettingsActivity.kt:320:17 Syntax error: Expecting an element.
```

**出错的写法**
```kotlin
val notifyOk = Build.VERSION.SDK_INT < Build.VERSION_CODES.TIRAMISU ||
        ContextCompat.checkSelfPermission(this, Manifest.permission.POST_NOTIFICATIONS)
        == PackageManager.PERMISSION_GRANTED
```

`==` 的优先级高于 `||`，且换行让 Kotlin 把 `==` 挂到了整个 `||` 表达式上。

**修法**：给右侧加括号。

```kotlin
val notifyOk = Build.VERSION.SDK_INT < Build.VERSION_CODES.TIRAMISU ||
        (ContextCompat.checkSelfPermission(this, Manifest.permission.POST_NOTIFICATIONS)
                == PackageManager.PERMISSION_GRANTED)
```

## 7. 其它静态审查中提前发现的问题

这些在编译前就改掉了，没进构建日志，但值得记：

| 位置 | 问题 | 修法 |
|---|---|---|
| `SpriteLoader` 缓存键 | `"a" + if (c) "b" else "" + "@$h"` —— `+` 只绑定了 else 分支，导致缓存键错乱 | 给三元加括号 |
| `PetService` 帧调度 | 同时用 Handler 和 Choreographer 排帧，会重复调度 | 统一用 Handler 固定 20ms（与引擎 TICK 对齐） |
| `PetService` | 通知栏有「收工」按钮，但 `onStartCommand` 没有 `ACTION_STOP` 分支 | 补上 |
| `SettingsActivity` | `requestOverlay()` 里 `startActivity` 和 `overlayLauncher.launch` 都调了，会开两次设置页 | 只用 launcher |
| `BootReceiver` | 自己发的 `ACTION_DELAYED_START` 广播没有处理分支 | 补上 |
| `PetService` | 定义了 `PetRuntime.isRunning` 但没人赋值，设置面板状态永远显示「未运行」 | 在 `onCreate` / `onDestroy` 里赋值 |
| `PetEngine` | 属性初始化顺序：`init{}` 里调 `dp()` 而 `density` 在 init 之后才赋值 | 改成构造参数注入 |
| `PetEngine` | 同时维护 `breathPhase` / `swayPhase` / `bobPhase` 三个相位，但原程序只用一个时间轴乘不同频率 | 合并成一个 `clock` |

## 9. 【重要更正】模拟器"卡死"的真实根因

这一条与桌宠代码无关，但**推翻了本项目早期的一个错误结论**，值得单独记下来。

### 错误结论

早期我在做模拟器参数对比实验时，多次遇到模拟器启动后一直 `offline`、
`qemu` 进程 CPU 时间几乎不涨。当时我判断为：

> "反复强杀导致 WHPX（Windows Hypervisor Platform）虚拟化会话进入坏状态，需要重启电脑"

这个结论**是错的**。

### 真实根因

后来抓完整日志，在 `Graphics backend: gfxstream` 之后看到：

```
Storing crashdata in: ...\emu-crash-37.2.12.db, detection is enabled for process: 33684
Showing crashdialog to get consent.          ← 弹一个"是否上报崩溃"的窗口
Attempting to send crashreport ... to https://clients2.google.com/cr/report
INFO | Report 312b72ad-... is available remotely as: ec01c9b508400000.
```

并用 `-WindowStyle Hidden` 启动。于是：

1. 模拟器在本机 GPU（Intel Arc B370）上初始化 Vulkan 时**真的崩溃了**
2. crashpad 弹出一个"是否上报崩溃"的**图形对话框**
3. 窗口是隐藏的，没人能点它
4. **进程就永久卡在那个对话框上**

所以它不是"卡在 GPU 初始化"，而是**卡在一个看不见的对话框上**。
`qemu` 进程不耗 CPU 也解释得通了 —— 它在等用户点击。

### 验证

用逐项隔离法（一次只改一个变量）测试四组参数，第一组就通过：

| 探测 | 参数 | 结果 |
|---|---|---|
| P1 | `-no-metrics -no-snapshot-save -no-boot-anim -memory 4096` | ✅ **booted=True，qemu 累计 CPU 140s** |
| P2/P3/P4 | 未执行（P1 已成功） | — |

`-no-metrics` 关掉崩溃上报后，**模拟器一次启动成功，从未重启电脑**。

### 教训

1. **不要把无法解释的失败归因为"环境坏了、重启试试"** —— 那是懒惰的解释。
   完整日志里一直写着答案（`Showing crashdialog to get consent.`），我只是没读到那一行。
2. **无头/隐藏窗口下启动 GUI 程序要警惕模态对话框**。它会静默吃掉整个进程。
   类似的还有：许可协议确认、首次运行向导、崩溃上报。
3. **`Start-Process -PassThru` 拿到的是启动器进程**，模拟器真正的进程是它 fork 的子进程。
   用 `$p.HasExited` 判断"启动失败"会误判 —— 要看 `qemu-system-*` 是否存活。

## 10. v1.1 尺寸功能改造

### 需求

> "能让这个桌宠再小一点吗（最小约占屏幕高度的 10% 左右，不然影响生活），
> 当然你再做一个 1.1 的版本，加入一个自由控制大小百分比的功能也是可以的"

### 改动

| 文件 | 改动 |
|---|---|
| `data/ConfigRepo.kt` | `PetSize` 从 enum 改成 object（常量 + `clamp` + `migrateLegacy`）；`size` 改成 `sizePercent: Int` |
| `engine/PetEngine.kt` | `size: PetSize` → `sizePercent: Int`；`applySize()` 用百分比算高度；新增 `MIN_PET_PX=96` 兜底 |

取值范围 8%~50%，步进 2%，默认 20%（比 v1.0 的 25% 更小）。

### 数据迁移

### 需求

> "1.2可以加入AI APK功能可以长按唤醒AI模式，暂时只做Ask mode，agent以后再说

官方当前（2026-10）的规格：

| base_url (OpenAI 兼容) | `https://api.deepseek.com` |
| model | `deepseek-flash`（旧名 `deepseek-v4-flash` 仍接受）/ `deepseek-v4-pro` |

如果照搬原代码，v1.2 一接入就 404。**这个坑靠读代码是发现不了的，必须查文档。**

| 双击 | 喂食面板 | **设置菜单** |
| 三指轻点 | — | **喂食面板** |

| 文件 | 职责 |
|---|---|
| `ai/AiClient.kt` | OpenAI 兼容的 `/chat/completions` 调用，**SSE 流式解析**，错误码翻译成中文 |
| `ai/ChatHistoryStore.kt` | 对话历史持久化，上限 40 条 |

### 技术要点

**1. 输入框的焦点问题（手机上最容易踩的坑）**

桌宠主悬浮窗是 `FLAG_NOT_FOCUSABLE`（否则抢走下面应用的触摸）。但输入框必须能拿焦点，
否则**软键盘弹不出来、也没法打字**。

所以 AI 面板是**独立的第二个悬浮窗**，且：
- 不带 `FLAG_NOT_FOCUSABLE` —— 允许获取焦点
- 带 `FLAG_ALT_FOCUSABLE_IM` —— 有焦点但不挡输入法
- `softInputMode = ADJUST_RESIZE` —— 键盘弹出时面板上移

实现时还得处理一个细节：鱼窗口在 AI 面板打开时**必须去掉 `FLAG_NOT_FOCUSABLE`**，
否则焦点和输入法可能被鱼抢走。这个逻辑统一放在 `applyInteractive()` 里。

实测结果：`Window #7 InputMethod` 成功连接，`adb shell input text` 能正常输入。

**2. 地址归一化**

用户填 base url 时写法五花八门，不该为此报错。`normalizeEndpoint()` 容错：

```
https://api.deepseek.com                          -> .../chat/completions
https://api.deepseek.com/v1                       -> .../v1/chat/completions
https://api.deepseek.com/v1/                      -> 同上
api.deepseek.com                                  -> 自动补 https://
https://api.deepseek.com/v1/chat/completions      -> 原样使用
```

**3. 零第三方依赖**

仍不引入 OkHttp / Gson，用 `HttpURLConnection` + 自写 SSE 行解析 + 原生 `org.json`。
整个 APK 只比 v1.1 大了 0.02 MB。

### 过程中自己引入又修掉的两个缺陷

**缺陷 1：设置面板的"让路"反噬了用户设置**

v1.1 为了让大鱼不挡住设置面板控件，我让面板打开时调 `PetService.setTouchable(false)`，
关闭时恢复。这个"恢复"用的原值 `interactiveBeforeSettings` 在
「先开面板 → 再启动桌宠」的时序下是 null（服务当时没运行，没记录），
于是 onPause 里"没值可恢复"，鱼回桌面后仍然摸不到。

第一版修法是给它兜底 `?: true`。结果更糟：**用户主动关掉「可互动」后，
一进出设置面板就被改回开启** —— 覆盖了用户的明确选择。

日志证据：

```
Settings.onResume running=false before=null cfgInt=true
Settings.onPause  running=true  before=null cfgInt=true
```

**最终修法**：把两个概念彻底拆开。

| 概念 | 存放处 | 谁写 |
|---|---|---|
| 用户意图（能不能摸鱼） | `ConfigRepo.interactive` | **只有复选框**（和通知栏切换） |
| 面板临时让路 | `PetRuntime.settingsVisible` | 设置面板的 onResume/onPause |

服务端统一裁决：

```kotlin
private fun shouldBeTouchable(): Boolean =
    config.interactive && !PetRuntime.settingsVisible
```

并新增 `ACTION_REFRESH_TOUCHABLE`：**只让服务重算一次 flags，不改任何配置**。
设置面板进出时发这个，而不是会写配置的 `ACTION_SET_TOUCHABLE`。

修复后实测：

| 场景 | 结果 |
|---|---|
| 面板打开中 | 穿透 ✓ |
| 回桌面（用户没改设置） | 可互动 ✓ |
| 用户关掉可互动 → 回桌面 | 穿透 ✓ |
| 再进出面板 | 复选框仍为 false，鱼仍穿透 ✓ |
| 勾回可互动 → 回桌面 | 可互动 ✓ |

**缺陷 2：首次引导跳过了面板**

原本没配 Key 时长按会直接跳设置页，用户根本不知道"长按"这个手势是干什么的。
改为**先弹出面板**，在面板里给一条可点击的引导（点它才跳设置）。

### 教训

1. **动工前查官方文档**。原代码里的模型名已停用一年，光读代码绝对发现不了。
2. **不要把"用户意图"和"系统临时状态"存在同一个字段里**。
   一旦两者都能写它，就必然出现互相覆盖。这次为此来回改了三版。
3. **写 UI 自动化测试时别用硬编码坐标**。我因为用了旧坐标导致复选框没点中，
   白测一轮才反应过来（实际坐标 1498，我用的是 1318）。

## 12. v1.2.1：GitHub 自动更新 + 修"鱼摸不到"的 bug

### 需求

> "加一个从github自动更新的功能。你试试能不能检测到我的github账号，上面应该有一个叫做
> dafeiyu-pet的仓库……（另外，你补一个bug,我发现每一次打开app是都会有1分钟左右
> 透明无法交互，你看看是什么问题）"

### 【教训】找账号要先查本地，别去搜公开仓库

我一开始上网搜 "dafeiyu-pet"，搜到 `1190fasheqi/dafeiyu-pet`（185 stars / 25 forks）
——那是**原作者的 Python 项目**，不是用户的仓库。用户当场纠正：
"在我的电脑上找github account 没让你去网上直接搜"。

正确的做法是查本地凭据，一次就找到：

```powershell
git config --global user.name          # DELTAfmc0906
gh auth status                          # ✓ Logged in as DELTAfmc0906
gh repo list DELTAfmc0906               # → dafeiyu-on-phone
```

**用户实际要用的仓库是 `DELTAfmc0906/dafeiyu-on-phone`**（已存在且为空仓库）。
如果按我搜到的那个去发布，就发到别人仓库去了。

### 卡顿 bug 的定位过程

**第一步：先排除"启动慢"**

加计时日志实测服务启动各阶段：

```
SpriteLoader 预热 24 张，耗时 83ms
after sprite/history +90ms
after startForeground +102ms
after createOverlay +171ms
after scheduleFrame +171ms
```

整个 `onCreate` 只要 **171ms**。所以"1 分钟"不是启动性能问题。

**第二步：区分「app 打不开」还是「鱼摸不到」**

逐秒采样窗口状态，三种场景：

| 场景 | 结果 |
|---|---|
| 全新打开 app（服务未运行） | app **立刻可交互**，无鱼窗口 |
| **鱼在后台跑着 → 打开 app** | **鱼持续 `NOT_TOUCHABLE` 长达 51 秒以上**（整个观察期）|
| 回桌面 | 立刻恢复 `可互动` |

**结论**：那 1 分钟"透明、点不动"的东西是**鱼**，不是 app 本身。
根因是 v1.1 引入的设计——为了避免鱼挡住设置面板控件，
让鱼在 app 前台期间自动触摸穿透。副作用就是用户开 app 时鱼一直"看得见但摸不到"。

（注：我没有复现出"app 界面本身点不动"。用户描述里这一部分存疑，
可能是主观感受，也可能与具体设备有关。已就此单独说明。）

**第三步：修法**

新增「**打开 app 时鱼也保持可互动**」开关（`config.forceInteractive`）：

```kotlin
private fun shouldBeTouchable(): Boolean {
    if (!config.interactive) return false      // 用户主动关了可互动
    if (config.forceInteractive) return true   // 用户要求 app 前台也可互动
    return !PetRuntime.settingsVisible         // 默认：面板打开时让路
}
```

实测（注入配置验证）：

```
未勾选：app 前台鱼=穿透，回桌面鱼=可互动
勾选后：app 前台鱼=可互动 ← 修复目标
日志：interactive=true force=true settingsVisible=false -> touchable=true
```

### 验证过程中自己犯的错

**`Get-Content` + `Set-Content` 破坏了 `build.gradle.kts`。**
我用一行 PowerShell 改版本号：

```powershell
(Get-Content app\build.gradle.kts) -replace ... | Set-Content app\build.gradle.kts -Encoding UTF8
```

结果：`Get-Content` 按 GBK 读（中文注释变乱码），`Set-Content -Encoding UTF8`（PS 5.1 会加 BOM）
再写回无 BOM 的文件；更糟的是**部分换行丢失，代码被并进注释行**：

```
// 鍥犱负 Kotlin DSL 閲?`java` 琚?Gradle 鐨?java 鎵╁睍閬斀浜嗐€?val keystorePropsFile = rootProject.file("key.properties")
                                                                    ^^^^ 这行被注释吃掉了
```

于是 `keystorePropsFile` 变成未定义，报一串 `Unresolved reference`。

**教训**：不要用 PowerShell 的文本管道改源码文件。要么用 `write`/`edit` 工具，
要么用 `[System.IO.File]::ReadAllText/WriteAllText` 并显式指定编码
（Kotlin/Gradle 文件用 **UTF-8 无 BOM**，PowerShell 脚本用 **UTF-8 with BOM**）。

**还有一个**：`adb install -r` 在签名不匹配时会**静默失败**（输出被管道吞掉），
导致我"验证"的其实是旧包，白测一轮。修法是先 `adb uninstall` 或检查 `$LASTEXITCODE`。

## 13. v1.2.2：修两个严重 bug（悬浮窗 → Activity）

### 用户反馈

> "AI聊天窗口可以调出但是点击对话框居然调动不了手机键盘，
> 另外，使用过大肥鱼AI对话功能并退出后，整个手机界面都被他控制，
> 点别的地方居然点不动只能拉动那个桌宠，必须开机重启"

### 根因：一个架构错误，两个症状

v1.2/v1.2.1 把 AI 对话界面做成了独立的 `TYPE_APPLICATION_OVERLAY` 悬浮窗。
**这个选择本身就是错的**，两个 bug 都是它的后果。

**症状 1：键盘弹得出来，但打字进不去**

`dumpsys input_method` 给出的决定性证据：

```
mCurrentFocus          = com.dafeiyu.pet          ← 窗口焦点拿到了
mIsInputViewShown      = true                     ← 键盘也显示了
mServedView            = DecorView{...别的Activity}  ← 但输入法连的是别的窗口
mServedInputConnection = null                     ← 输入连接为空
```

**悬浮窗可以获得窗口焦点，但输入法不会为它建立 InputConnection。**
我试过加 `FLAG_ALT_FOCUSABLE_IM`、`SOFT_INPUT_STATE_ALWAYS_VISIBLE`、
多次重试 `showSoftInput` —— 都没用。文本输入必须有正常的窗口令牌。

**症状 2：退出后整个手机点不动，只能重启**

悬浮窗不归 Activity 生命周期管。一旦没被正确 `removeView`
（例如服务被系统杀掉、或异常路径），它就会残留成一个"孤儿窗口"，
持续拦截全局触摸。用户唯一能做的就是重启。

### 修法：改成透明浮层 Activity

新建 `ChatActivity`（`Theme.MaterialComponents.DayNight.Dialog` +
`windowIsFloating` + 透明背景 + 底部对齐 + `dimAmount 0.25`），
观感与原来的悬浮面板一致，但拿到的是正常窗口令牌和系统托管的生命周期。

同时把纯 View 部分抽成 `AiChatPanelView`（不含任何窗口管理），
删掉旧的 `AiChatPanel.kt`。

**另外修掉一处早期引入的错误**：v1.2/v1.2.1 会在对话界面打开时
**去掉桌宠窗口的 `FLAG_NOT_FOCUSABLE`**。这也是错的 ——
同一时刻只能有一个窗口持有输入焦点，桌宠一旦变成可聚焦就会跟对话界面抢。
现在桌宠窗口**永远**保持 `FLAG_NOT_FOCUSABLE`。

### 修复后实测

```
mServedInputConnection = RemoteInputConnectionImpl{...}   ← 已建立（修复前 null）
前台 Activity          = com.dafeiyu.pet/.ui.ChatActivity
打字                   → 输入框内容 = [test123] ✓
按返回关闭对话 → 回桌面 → 鱼 = 可互动 ✓
退出后打开系统设置      → 正常 ✓（全局触摸未被吃）
强制杀死 app           → dafeiyu 窗口数 = 0，无孤儿窗口 ✓
```

### 过程中又一个自己踩的坑

**`chatVisible` 复位放错了生命周期**。

第一版把 `PetRuntime.chatVisible = false` 放在 `onDestroy`。但用户按返回键时
Activity 通常只走到 `onStop`（实例保留以便复用），`onDestroy` 不触发 →
标记一直是 true → 桌宠**永久**处于触摸穿透。

实测抓到：

```
[A] 按返回关闭对话 → 鱼 = 穿透
[B] 回桌面        → 鱼 = 穿透   ← 应该是「可互动」
```

改成在 `onPause` 复位（`onResume` 置位），并调用
`PetService.refreshTouchable()` 让服务立刻重算 flags。

**教训**：状态标记的复位要挂在"不再可见"的生命周期点上，
而不是"被销毁"。Android 的 Activity 在返回后常常还活着。

### 还有一个反复踩的坑

**`adb install -rf` 在签名不匹配时静默失败**，害我"验证"了两轮旧包。
这次是靠核对 `dumpsys package` 里的 `versionName` 才发现的。
以后一律：先 `adb uninstall`，再 `adb install`，最后核对版本号。

## 14. v1.2.3：修 `null` 串 + 语音输入

### 用户反馈（附 API Key 让我实测）

> "你用API实测一下（sk-...），莫名其妙的在对话中出现了bug，
> 输出一大段"nullnullnull...."然后就没有实际的输出，
> 另外，这个对话UI太简陋了，能不赛一个语音识别进去然后加一个按住说话功能"

### 用真实 API 定位 bug

拿到 Key 后第一件事不是改代码，而是**抓原始响应**。

**非流式请求的结果就已经暴露问题**：

```json
"message": {
    "content": "",                                  ← 正文空的
    "reasoning_content": "We need answer to user..."  ← 内容全在这
},
"finish_reason": "length",                          ← 被长度截断
"completion_tokens_details": { "reasoning_tokens": 50 }
```

**流式请求的原始 SSE 直接坐实了 `null` 的来源**：

```
data: {"delta":{"content":null,"reasoning_content":"我们需 要"}}
data: {"delta":{"content":null,"reasoning_content":"回答"}}
data: {"delta":{"content":null,"reasoning_content":"用户"}}
```

**两个根因**：

1. **`org.json` 的 `optString` 陷阱**
   我的代码写的是 `.optString("content")`。
   `optString` 在 key 存在、值为 JSON `null` 时，会返回**字符串 `"null"`**
   （它只判断 key 在不在，不做空值判断）。
   于是每一帧都往气泡追加一个字面量 `null` → 用户看到 `nullnullnull...`。

2. **`max_tokens` 太小**
   我原来设 200。而 `deepseek-flash` 思考一次能产出 **73KB**（实测），
   token 全被 `reasoning_content` 烧光，正文 `content` 永远是空，
   `finish_reason` 直接是 `length`。

**顺便实测出思考开关的效果**：

| 请求 | 响应体积 | 有 reasoning_content |
|---|---|---|
| `thinking:{type:enabled}` | 81 KB | 是 |
| `thinking:{type:disabled}` | **1.5 KB** | 否 |
| 不传该参数（默认） | 53 KB | 是 |

差 54 倍。所以把「显示思考过程」做成配置项，**默认关闭**。

**修法**：

```kotlin
private fun JSONObject.optStringOrNull(key: String): String? {
    if (!has(key) || isNull(key)) return null
    return optString(key, "")
}
```

- 正文与思考分别累积、分别回调
- `max_tokens` 提到 2048（开思考）/ 600（关思考）
- 识别 `finish_reason == "length"` 并明确提示
- 思考以灰色斜体气泡显示，样式对齐原 Python 版的「思维链心声」

### 语音输入（按住说话）

用系统自带的 `SpeechRecognizer`，**不引入任何第三方 SDK**：

```
按下 -> startListening
松开 -> stopListening（立刻结束并取回结果）
```

配合 `EXTRA_PARTIAL_RESULTS` 能做到边说边显示。
`EXTRA_SPEECH_INPUT_COMPLETE_SILENCE_LENGTH_MILLIS` 设成 60 秒，
关掉"自动断句"，把结束时机交给按键。

Android 11+ 必须在 Manifest 里声明包可见性，否则
`SpeechRecognizer.isRecognitionAvailable()` 永远返回 false：

```xml
<queries>
    <intent><action android:name="android.speech.RecognitionService" /></intent>
</queries>
```

### 自查出的一个崩溃

首次装到模拟器后长按无反应，logcat 显示：

```
FATAL EXCEPTION: kotlin.UninitializedPropertyAccessException:
    lateinit property micBtn has not been initialized
```

原因：我在 `micBtn = TextView(...).apply { ... attachHoldToTalk() }` 里
**在 apply 块内部**调用了会读 `micBtn` 的方法，
而那一刻 `lateinit` 的赋值还没完成。

修法：把 `attachHoldToTalk()` 移到 `build()` 末尾，所有 View 赋值完毕后再挂监听。

**教训**：`lateinit` + `apply {}` 里回调自身属性，是典型的初始化顺序陷阱。
构造 View 树时，监听器统一在最后挂。

### 真实 API 实测结果

主机直连 `api.deepseek.com` 返回 HTTP 200。
模拟器第一次报「连不上服务器」——原因是**模拟器 IPv6 不通**
（logcat 里 `connectivitycheck.gstatic.com` 同样 10 秒超时），
重置网络后成功：

```
输入: hi
回复: 哟~主人来啦！今天也是闲得慌来找我玩吗？
```

**`null` 串彻底消失，输出为正常中文。**

### 语音功能的验证边界

模拟器上点 🎤 返回「网络错误，识别失败」。
这**恰恰证明链路是通的**：按钮响应 → 权限通过 → SpeechRecognizer 启动 →
失败发生在连接**谷歌识别服务**这一步（模拟器访问不到 Google）。
app 代码无误，需真机验证。

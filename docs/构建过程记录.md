## 1. 忘了 `gradle-wrapper.properties`

**报错**
```
java.lang.RuntimeException: Wrapper properties file
'...\gradle\wrapper\gradle-wrapper.properties' does not exist.
```

**原因**：工程是手工搭的骨架，只从模板工程拷了 `gradlew` / `gradlew.bat` / `gradle-wrapper.jar`，
漏了这个 properties 文件。

**修法**：补上，并把 `distributionUrl` 指向腾讯云镜像（否则要从 services.gradle.org 拉，国内很慢）。

```properties
distributionUrl=https\://mirrors.cloud.tencent.com/gradle/gradle-9.8.1-bin.zip
```

## 2. `key.properties` 带 UTF-8 BOM 导致签名读不到

**报错**
```
* Where: Build file '...\app\build.gradle.kts' line: 29
* What went wrong:
getProperty(...) must not be null
```

**排查过程**：对比了本项目与能正常构建的 HelloAndroid 的 `key.properties`，发现字节差异：

```
本项目     前3字节 = 239,187,191   ← UTF-8 BOM (EF BB BF)
HelloAndroid 前3字节 = 35,32,231     ← "# " 无 BOM
```

BOM 会粘在**第一个键名**上，`storeFile` 实际变成了 `\uFEFFstoreFile`，
所以 `getProperty("storeFile")` 返回 null。

**修法（两道）**：

1. 写文件时用 `UTF8Encoding($false)` 明确不要 BOM
2. 构建脚本里加防御，主动剥掉 BOM 键名：

```kotlin
val bomKeyName: String? = keystoreProps.stringPropertyNames()
    .firstOrNull { it.startsWith('\uFEFF') }
if (bomKeyName != null) { /* 改名 */ }
```

> 教训：`.properties` / `.xml` 之外的配置文件尽量别有 BOM，
> Windows 上的 `Set-Content -Encoding UTF8`（PowerShell 5.1）会加 BOM。

## 3. Kotlin DSL 类型推断递归

**报错**
```
e: app/build.gradle.kts:17:22: Type checking has run into a recursive problem.
   Easiest workaround: specify the types of your declarations explicitly.
e: app/build.gradle.kts:17:36: Unresolved reference 'stringPropertyNames'.
```

**出错的写法**
```kotlin
val keystoreProps = Properties().apply {      // 没写类型
    if (...) keystorePropsFile.inputStream().use { load(it) }
}
// 后面又引用 keystoreProps.stringPropertyNames() ...
```

**原因**：`apply {}` 的接收者类型依赖 `keystoreProps` 的推断类型，
而 `keystoreProps` 的类型又依赖 `apply {}` 内部的引用 —— 循环了。

**修法**：显式声明类型，并且不要在 `apply` 块里回引自己。

```kotlin
val keystoreProps: Properties = Properties()
if (keystorePropsFile.exists()) {
    keystorePropsFile.inputStream().use { stream -> keystoreProps.load(stream) }
}
```

> 同类问题也出现在 `java.util.Properties()`：Kotlin DSL 里 `java` 被 Gradle 的
> `java` 扩展遮蔽，必须 `import java.util.Properties` 后用短名。

## 4. Kotlin 字符串模板里中文紧跟变量名

**报错**
```
e: Lines.kt:85:67 Unresolved reference 'city今天'.
```

**出错的写法**
```kotlin
fun weatherLine(city: String, temp: String, desc: String) = "$city今天${temp}°，天气$desc"
```

Kotlin 把 `city今天` 当成一个标识符了 —— 它允许标识符里含中文，
所以 `$city今天` 会被解析为变量 `city今天`。

**修法**：用花括号把变量名括起来。

```kotlin
"${city}今天${temp}°，天气$desc"
```

## 5. `coerceAtLeast` 的类型不匹配

**报错**
```
e: PetEngine.kt:336:63 Argument type mismatch: actual type is 'Float', but 'Int' was expected.
```

**出错的写法**
```kotlin
val hiX = (screenW - petWidth - dp(40)).coerceAtLeast(loX + 1f)
//    ^^^ Int 表达式                              ^^^ Float 参数
```

**修法**：先转 Float 再 coerce。

```kotlin
val hiX = (screenW - petWidth - dp(40)).toFloat().coerceAtLeast(loX + 1f)
```

## 6. `||` 与换行导致的布尔判断错位

**报错**
```
e: SettingsActivity.kt:319:17 Condition type mismatch: inferred type is 'Int' but 'Boolean' was expected.
e: SettingsActivity.kt:320:17 Syntax error: Expecting an element.
```

**出错的写法**
```kotlin
val notifyOk = Build.VERSION.SDK_INT < Build.VERSION_CODES.TIRAMISU ||
        ContextCompat.checkSelfPermission(this, Manifest.permission.POST_NOTIFICATIONS)
        == PackageManager.PERMISSION_GRANTED
```

`==` 的优先级高于 `||`，且换行让 Kotlin 把 `==` 挂到了整个 `||` 表达式上。

**修法**：给右侧加括号。

```kotlin
val notifyOk = Build.VERSION.SDK_INT < Build.VERSION_CODES.TIRAMISU ||
        (ContextCompat.checkSelfPermission(this, Manifest.permission.POST_NOTIFICATIONS)
                == PackageManager.PERMISSION_GRANTED)
```

## 7. 其它静态审查中提前发现的问题

这些在编译前就改掉了，没进构建日志，但值得记：

| 位置 | 问题 | 修法 |
|---|---|---|
| `SpriteLoader` 缓存键 | `"a" + if (c) "b" else "" + "@$h"` —— `+` 只绑定了 else 分支，导致缓存键错乱 | 给三元加括号 |
| `PetService` 帧调度 | 同时用 Handler 和 Choreographer 排帧，会重复调度 | 统一用 Handler 固定 20ms（与引擎 TICK 对齐） |
| `PetService` | 通知栏有「收工」按钮，但 `onStartCommand` 没有 `ACTION_STOP` 分支 | 补上 |
| `SettingsActivity` | `requestOverlay()` 里 `startActivity` 和 `overlayLauncher.launch` 都调了，会开两次设置页 | 只用 launcher |
| `BootReceiver` | 自己发的 `ACTION_DELAYED_START` 广播没有处理分支 | 补上 |
| `PetService` | 定义了 `PetRuntime.isRunning` 但没人赋值，设置面板状态永远显示「未运行」 | 在 `onCreate` / `onDestroy` 里赋值 |
| `PetEngine` | 属性初始化顺序：`init{}` 里调 `dp()` 而 `density` 在 init 之后才赋值 | 改成构造参数注入 |
| `PetEngine` | 同时维护 `breathPhase` / `swayPhase` / `bobPhase` 三个相位，但原程序只用一个时间轴乘不同频率 | 合并成一个 `clock` |

## 9. 【重要更正】模拟器"卡死"的真实根因

这一条与桌宠代码无关，但**推翻了本项目早期的一个错误结论**，值得单独记下来。

### 错误结论

早期我在做模拟器参数对比实验时，多次遇到模拟器启动后一直 `offline`、
`qemu` 进程 CPU 时间几乎不涨。当时我判断为：

> "反复强杀导致 WHPX（Windows Hypervisor Platform）虚拟化会话进入坏状态，需要重启电脑"

这个结论**是错的**。

### 真实根因

后来抓完整日志，在 `Graphics backend: gfxstream` 之后看到：

```
Storing crashdata in: ...\emu-crash-37.2.12.db, detection is enabled for process: 33684
Showing crashdialog to get consent.          ← 弹一个"是否上报崩溃"的窗口
Attempting to send crashreport ... to https://clients2.google.com/cr/report
INFO | Report 312b72ad-... is available remotely as: ec01c9b508400000.
```

并用 `-WindowStyle Hidden` 启动。于是：

1. 模拟器在本机 GPU（Intel Arc B370）上初始化 Vulkan 时**真的崩溃了**
2. crashpad 弹出一个"是否上报崩溃"的**图形对话框**
3. 窗口是隐藏的，没人能点它
4. **进程就永久卡在那个对话框上**

所以它不是"卡在 GPU 初始化"，而是**卡在一个看不见的对话框上**。
`qemu` 进程不耗 CPU 也解释得通了 —— 它在等用户点击。

### 验证

用逐项隔离法（一次只改一个变量）测试四组参数，第一组就通过：

| 探测 | 参数 | 结果 |
|---|---|---|
| P1 | `-no-metrics -no-snapshot-save -no-boot-anim -memory 4096` | ✅ **booted=True，qemu 累计 CPU 140s** |
| P2/P3/P4 | 未执行（P1 已成功） | — |

`-no-metrics` 关掉崩溃上报后，**模拟器一次启动成功，从未重启电脑**。

### 教训

1. **不要把无法解释的失败归因为"环境坏了、重启试试"** —— 那是懒惰的解释。
   完整日志里一直写着答案（`Showing crashdialog to get consent.`），我只是没读到那一行。
2. **无头/隐藏窗口下启动 GUI 程序要警惕模态对话框**。它会静默吃掉整个进程。
   类似的还有：许可协议确认、首次运行向导、崩溃上报。
3. **`Start-Process -PassThru` 拿到的是启动器进程**，模拟器真正的进程是它 fork 的子进程。
   用 `$p.HasExited` 判断"启动失败"会误判 —— 要看 `qemu-system-*` 是否存活。

## 10. v1.1 尺寸功能改造

### 需求

> "能让这个桌宠再小一点吗（最小约占屏幕高度的 10% 左右，不然影响生活），
> 当然你再做一个 1.1 的版本，加入一个自由控制大小百分比的功能也是可以的"

### 改动

| 文件 | 改动 |
|---|---|
| `data/ConfigRepo.kt` | `PetSize` 从 enum 改成 object（常量 + `clamp` + `migrateLegacy`）；`size` 改成 `sizePercent: Int` |
| `engine/PetEngine.kt` | `size: PetSize` → `sizePercent: Int`；`applySize()` 用百分比算高度；新增 `MIN_PET_PX=96` 兜底 |
| `ui/SettingsActivity.kt` | 三档 Spinner → `SeekBar` + 实时百分比文字 + 三档快捷按钮 |
| `ui/PetMenu.kt` | 长按菜单里新增 `showSizeDialog()`，同样是滑杆（拖动即时生效） |
| `res/values/strings.xml` | 新增 `size_current`、`size_hint` |

取值范围 8%~50%，步进 2%，默认 20%（比 v1.0 的 25% 更小）。

### 数据迁移

v1.0 存的是字符串档位（`"small"`/`"medium"`/`"large"`），v1.1 存 Int 百分比。
`ConfigRepo.sizePercent` 的 getter 做了兼容：新键没有就读旧键并迁移，
迁移后顺手写回新键，避免每次读都走迁移分支。

| 快捷「小」 | 10% | 242px | 242.4 | 242×357 |
| 快捷「中」 | 20% | 484px | 484.8 | 484×648 |

## 11. v1.2：AI 对话功能

### 需求

> "1.2可以加入AI APK功能可以长按唤醒AI模式，暂时只做Ask mode，agent以后再说
> （第一次长按时提示输入deepseek api，也可以在app内设置openai格式的API）"

### 关键前置发现

动工前先查了 DeepSeek 官方文档，发现**原 Python 代码里的模型名已经失效**：

```python
# 桌宠.py 第 46 行（原版）
DS_MODEL = "deepseek-chat"
```

`deepseek-chat` / `deepseek-reasoner` 已于 **2025-07-24 停用**。
官方当前（2026-10）的规格：

| 项 | 值 |
|---|---|
| base_url (OpenAI 兼容) | `https://api.deepseek.com` |
| model | `deepseek-flash`（旧名 `deepseek-v4-flash` 仍接受）/ `deepseek-v4-pro` |

如果照搬原代码，v1.2 一接入就 404。**这个坑靠读代码是发现不了的，必须查文档。**

| 双击 | 喂食面板 | **设置菜单** |

| 文件 | 职责 |
|---|---|
| `ai/AiClient.kt` | OpenAI 兼容的 `/chat/completions` 调用，**SSE 流式解析**，错误码翻译成中文 |
| `ai/ChatHistoryStore.kt` | 对话历史持久化，上限 40 条 |

### 技术要点

**1. 输入框的焦点问题（手机上最容易踩的坑）**

桌宠主悬浮窗是 `FLAG_NOT_FOCUSABLE`（否则抢走下面应用的触摸）。但输入框必须能拿焦点，
否则**软键盘弹不出来、也没法打字**。

所以 AI 面板是**独立的第二个悬浮窗**，且：
- 不带 `FLAG_NOT_FOCUSABLE` —— 允许获取焦点
- 带 `FLAG_ALT_FOCUSABLE_IM` —— 有焦点但不挡输入法
- `softInputMode = ADJUST_RESIZE` —— 键盘弹出时面板上移

实现时还得处理一个细节：鱼窗口在 AI 面板打开时**必须去掉 `FLAG_NOT_FOCUSABLE`**，
否则焦点和输入法可能被鱼抢走。这个逻辑统一放在 `applyInteractive()` 里。

实测结果：`Window #7 InputMethod` 成功连接，`adb shell input text` 能正常输入。

**2. 地址归一化**

用户填 base url 时写法五花八门，不该为此报错。`normalizeEndpoint()` 容错：

```
https://api.deepseek.com                          -> .../chat/completions
https://api.deepseek.com/v1                       -> .../v1/chat/completions
https://api.deepseek.com/v1/                      -> 同上
api.deepseek.com                                  -> 自动补 https://
https://api.deepseek.com/v1/chat/completions      -> 原样使用
```

**3. 零第三方依赖**

仍不引入 OkHttp / Gson，用 `HttpURLConnection` + 自写 SSE 行解析 + 原生 `org.json`。
整个 APK 只比 v1.1 大了 0.02 MB。

### 过程中自己引入又修掉的两个缺陷

**缺陷 1：设置面板的"让路"反噬了用户设置**

v1.1 为了让大鱼不挡住设置面板控件，我让面板打开时调 `PetService.setTouchable(false)`，
关闭时恢复。这个"恢复"用的原值 `interactiveBeforeSettings` 在
「先开面板 → 再启动桌宠」的时序下是 null（服务当时没运行，没记录），
于是 onPause 里"没值可恢复"，鱼回桌面后仍然摸不到。

第一版修法是给它兜底 `?: true`。结果更糟：**用户主动关掉「可互动」后，
一进出设置面板就被改回开启** —— 覆盖了用户的明确选择。

日志证据：

```
Settings.onResume running=false before=null cfgInt=true
Settings.onPause  running=true  before=null cfgInt=true
```

**最终修法**：把两个概念彻底拆开。

| 概念 | 存放处 | 谁写 |
|---|---|---|
| 用户意图（能不能摸鱼） | `ConfigRepo.interactive` | **只有复选框**（和通知栏切换） |
| 面板临时让路 | `PetRuntime.settingsVisible` | 设置面板的 onResume/onPause |

服务端统一裁决：

```kotlin
private fun shouldBeTouchable(): Boolean =
    config.interactive && !PetRuntime.settingsVisible
```

并新增 `ACTION_REFRESH_TOUCHABLE`：**只让服务重算一次 flags，不改任何配置**。
设置面板进出时发这个，而不是会写配置的 `ACTION_SET_TOUCHABLE`。

修复后实测：

| 场景 | 结果 |
|---|---|
| 面板打开中 | 穿透 ✓ |
| 回桌面（用户没改设置） | 可互动 ✓ |
| 用户关掉可互动 → 回桌面 | 穿透 ✓ |
| 再进出面板 | 复选框仍为 false，鱼仍穿透 ✓ |
| 勾回可互动 → 回桌面 | 可互动 ✓ |

**缺陷 2：首次引导跳过了面板**

原本没配 Key 时长按会直接跳设置页，用户根本不知道"长按"这个手势是干什么的。
改为**先弹出面板**，在面板里给一条可点击的引导（点它才跳设置）。

### 教训

1. **动工前查官方文档**。原代码里的模型名已停用一年，光读代码绝对发现不了。
2. **不要把"用户意图"和"系统临时状态"存在同一个字段里**。
   一旦两者都能写它，就必然出现互相覆盖。这次为此来回改了三版。
3. **写 UI 自动化测试时别用硬编码坐标**。我因为用了旧坐标导致复选框没点中，
   白测一轮才反应过来（实际坐标 1498，我用的是 1318）。
